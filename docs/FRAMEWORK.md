# 自动科研框架（草案 v0，2026-11-05）

目标：让一组 agent 持续、高并行地推进一个研究目标；人只在少数真正需要人的地方出手，出手时看得懂。
本文是通用框架，不针对任何具体项目。依据见末尾"参考"。

---

## 0. 四条原则

1. **机制优先于提示词。** 并行度、审查力度、决策权限都写成脚本规则和数字，不靠"请尽量并行"这类话。
2. **执行才是真相，评审只挑毛病。** 能跑实验、跑测试、对参考答案的，就不靠模型意见。
3. **状态在文件里，不在对话里。** agent 用完即弃，任何时候重启都能接上。
4. **人管"要什么"和"付什么代价"，不管"技术上对不对"。** 人的认知不一定高于旗舰模型；技术判断留在 AI 之间，靠证据收敛。

---

## 1. 任务图：router 和 worker 是同一张图上的节点

- 整个项目是**一张动态任务图**。节点有两种结果：
  - **worker 节点**：交出产物（代码、数据、结论）和自验收结果，然后关闭；
  - **router 节点**：交出一段**子图提议**（新节点、依赖、各自的写域、预算、验收标准）。子图里可以再有 router，递归展开。
- 任何节点做完都可以改变图：失败节点只让**它的父 router** 局部重规划（换做法、加调试分支、剪枝），不重排全图。
- **改图要过闸门（脚本，不是模型）**：router 只能提议，控制器检查后才写入：
  - 无环；深度 ≤ 8，单次分出 ≤ 12，总节点数和子树预算不超父节点下发的额度；
  - 子节点写域在父节点写域之内，兄弟节点写域不重叠；
  - 每个节点有验收标准（写在拆分时，不在交付时）；
  - 提议引用了依据（上游结果、失败记录、文献）。
- 节点类型：`plan`（router）/ `run`（实现、实验）/ `check`（独立验证，少用，见 §4）/ `decide`（需要裁决，见 §5）。

## 2. 调度：真正独立的活不漏派，串行的活不硬拆

并行度是**上限**，不是指标。目标是"关键路径最短"，不是"同时跑的 agent 最多"。多 agent 在必须按顺序推进的任务上反而更差（最多差 70%），错误还会被放大。

- **一个全局就绪队列，不分批等待。** 任何层级、依赖已满足的节点进队，有空位就派；**并行上限**默认不设，需要时按资源声明（内存/GPU/预算）。有节点完成时立即补位，另有定时兜底。
- **router 拆分时必须标明结构**：每段子图标为 `serial`（后一步依赖前一步的结果、或共享同一份正在改的状态）或 `parallel`（输入独立、写域不重叠、结果可以分别验收）。闸门检查：标 `parallel` 的兄弟节点写域不重叠、各自有独立验收标准；拆不出这两条的就按 `serial` 走。
- **串行段一次只跑一个节点**，用一个连续的 worker 做完一整段比拆给多人接力更好（少交接、少上下文丢失）。
- **只在存在真正独立的活时才扩展。** 调度器唤醒 router 的条件不是"并行位空着"，而是"有可并行的工作却没派出去"的信号：
  1. 验证器报出**多个不同的**失败（不同测试、不同错误类别、对参考实现的不同差异）——每个一张单；
  2. 需要比较的**多个候选**（替代方案、参数点、变体），彼此不依赖；
  3. 主路径之外**确有价值**的独立工作（消融、复现、敏感性分析），由 router 判断值得做才加，不为填空位而加。
  
  没有这些信号时，空着的并行位就让它空着。
- **检测塌缩**：多个 worker 撞上同一个失败、或在改同一处 → 停止加人，交回父 router 重新拆分或改为串行。
- **按关键路径计分**：多开的节点只有缩短最长链才算有效；巡检看的是"关键路径上有没有在等"，不是"有几个空位"。
- **每个 run 节点有固定预算**（时间/调用/算力），超了就交付当前最好结果或标失败，不无限跑。

## 3. 节点与 agent

- **worker 用完即弃**：只拿到自己的目标、依赖的结果、父计划摘要和共享"发现记录"；交付后由脚本关闭终端。
- **交付格式固定**：结论 / 证据（文件、日志行、提交号、数字）/ 自验收结果 / 已知局限 / 建议的后续节点。
- **共享发现记录**：经过验收的结论和失败教训写进一份结构化记录，后续节点读它而不是读别人的对话。
- **节点粒度**：一个节点完成一件可以自己验收的事（经验值 30 分钟–2 小时），避免切得过碎导致派发和审查的固定开销占大头。
- **数据反驳即止损**：结果显示方向不成立（对照追平或超过核心方法），父 router 直接剪掉该分支，不写"再跑几次就好"。

## 4. 审查：按分量配，有硬上限

| 场合 | 怎么验 | 谁 |
|---|---|---|
| 普通 run 交付 | 节点自己跑验收标准；父 router 看交付记录，接受或打回 | 无额外节点 |
| 关键结论（里程碑、改方向、对外的数字） | 一次 `check` 节点，只读、新上下文、只看产物和证据，审一轮 | 与作者**不同家族**的模型 |
| 替人做裁决（§5 第二档） | 两家旗舰模型各自独立审，投票 | 如 Opus + Astra |

- **硬上限**：审查耗时 ≤ 执行耗时的 20%；超标由巡检提醒。不通过就开新的 run 节点修，不反复审同一份。
- **审查不挡路**：审查进行时，空位照常派别的节点。
- **评估器冻结**：打分代码、测试集、参考答案对被评对象只读且尽量不可见；留一部分隐藏用例，比较可见与隐藏分数是否一致（防"改打分器"）。

### 专家角色提示词怎么写

证据表明"你是资深专家"这句对准确率基本没用；有用的是**审什么、怎么审**。每个领域的 reviewer/judge 提示词由四块组成：

1. **角色与范围**（一两句，定口吻和边界，不指望它提升准确率）；
2. **领域失效清单**（逐项 PASS/FAIL）：例如数字无出处、对照没重跑、参数被意外固定、测试数据泄漏、改了评估代码、结论强于效应量、只报好结果；
3. **程序**：列出结论依赖的假设 → 逐条对证据核对（必须引用文件/日志行）→ 推演可能的失败情形 → 给出"什么证据会推翻这个结论"；
4. **立场**：默认对抗，"没把握就判不通过"，至少写一个可能错的具体理由；自报置信度只作参考，以面板一致度为准。

### 模型自己也不够懂的领域

- **先测**：每个领域准备几道已知答案的题，新开的专家角色先答；错得多的领域标为"模型弱"。
- **弱领域的结论**必须有实验、参考实现或文献支撑才算数，单靠模型判断不收。
- **两家模型分歧大、或结论找不到出处**，视为能力边界信号：生成"补证据"节点（小实验、找文献、找参考实现），而不是直接问人。
- 只有当补证据需要人才拿得到的东西时（领域专家、实验数据、付费资源），才升级给人——问的是"去哪拿证据、花不花这份代价"，不是"你觉得对不对"。

## 5. 决策：什么时候才找人

git 让代码和文档几乎都能回退，所以"能不能撤回"不是标准。真正要人的只有下面几类：

| 触发条件 | 例子 |
|---|---|
| **目标与价值** | 改最终目标、成功标准、范围；伦理或安全问题 |
| **git 撤不回的代价** | 花钱/算力超预算；对外发布、投稿、发消息、调用外部服务；删除版本库之外的数据；动共享资源（别人的机器、磁盘、账号） |
| **留出集** | 任何一次读取最终测试集（看过就失效） |
| **只有人有的真值** | 实验室数据、领域访问权限、"这是不是你要的" |
| **关键结论上面板分歧** | 两家模型投票不一致，或可见/隐藏分数背离 |
| **反复失败** | 同一节点超过重试上限、或检测到原地打转 |

除此之外（实验设计、技术取舍、方法选择、bug）都在 AI 之间闭环：
- **第一档——可直接核对**：验证器直接判。
- **第二档——技术裁决**：两家模型独立判断，一致就执行并记入**每日汇总**，人可以事后推翻（git 回退）；不一致就先补证据，补完仍分歧才升到第三档。
- **第三档——上表的触发条件**：挂起该分支、推送给人；其他分支照常推进；人一直不回，按目标契约里预先写好的默认处理。

## 6. 和人的沟通

- **目标契约**：一份 `program.md`（最终目标、成功标准、预算、禁止事项、各类默认处理）。agent 通过提问帮人起草，人签字后生效；人只在改方向时改它。
- **推送渠道**：通过 Hermes 发到 QQ（`hermes send`，脚本直接发，不经模型）。只推第三档；第二档进每日汇总。
- **决策卡片格式**（为了让不熟悉的人边看边懂，也防止被单方说服）：
  1. 一句话：要定什么、为什么现在定、代价是什么（"不可撤回：花 X / 对外发布 Y"）；
  2. 一段白话背景，术语当场解释；
  3. **先请人给出直觉选择**，再展开 AI 意见（减少盲从）；
  4. **正反两方**：由两个独立 agent 各写一段，各自引用证据——双方辩论比单方陈述更能帮非专家判断对；
  5. 面板投票结果、分歧点、"什么证据会改变结论"；
  6. 不回会怎样；证据链接。
- **回复**：回"选 2"直接生效；回"为什么/解释 X"，agent 用白话再展开一层。
- **闭环学习**：每个决定事后记录结果（哪一方对了），下次相关决策时附上，让人逐步建立判断。

## 7. 巡检：外层的自动循环

便宜脚本每几分钟一轮，模型巡检员每半小时一轮。它不干活，只看指标并调整：

| 指标 | 超标时 |
|---|---|
| 就绪但未派出的节点 × 小时（漏派） | 立即派发；查调度器 |
| 关键路径停滞时长（没有任何节点在推进最长链） | 唤醒对应 router：是在等依赖、在等人、还是没想好下一步 |
| 标为 parallel 的兄弟节点撞同一失败 / 改同一处 | 判为拆错，改回串行 |
| 等人 × 小时 | 检查是否把第二档误放进第三档 |
| 审查耗时 / 执行耗时 | > 20% 提醒放宽审查 |
| 每小时新增的已验收发现 | 长时间为零，提议剪掉该分支或换方向 |
| 同一节点打回次数 | 超限判为打转，上报 |
| 多 worker 撞同一失败 | 判为塌缩，交回重拆 |

另有：报错自动"继续"、agent 掉线后由其他节点接手、磁盘/内存告警。分支之间的预算按产出动态分配。

**关闭空闲 worker 与 QQ 告警。** router 用 `orchestration dispatch` 派进自己开的终端的 worker，Orca 报 `retained`，`worker-release` 对它们没有效果，终端会空转几小时。巡检因此直接关：任务已结束、不在输出（标题无转圈）、屏幕停在输入框、且空闲 ≥ 30 分钟（对不上节点的要 ≥ 120 分钟）的 worker 终端，先试 worker-release，没释放就 `orca terminal close`；同一终端最多试 2 次，再失败就发告警。QQ 告警（`alerts.py`）只管"需要人看"的事：巡检自己看不见（快照过期、主机连不上、屏幕读取大面积失败）、worker 连续报错且自动继续用完、关闭失败、巡检员留给人或 tooling 的待办、就绪节点连续派不出去（`undispatchable:<线>`，同一节点同一原因连续 2 轮或 30 分钟）、巡检代派被 Orca 拒绝满 3 次（`dispatch_rejected:<线>:<节点>`）。每条告警出现时立刻发一次，之后在 2、8、24 小时各提醒一次（最多 4 次，再不发但保留），条件消失时发一次"[已恢复]"；同一轮的多条合并成一条消息，不刷屏。

**全局故障与停摆告警。** 11-06 夜里模型网关（magpie）挂了 6.5 小时，所有 agent 停在 "API Error: 504 … try again"，没人通知用户。现在巡检每轮检查两件事并走 QQ：`outage:model`（本轮至少 2 个不同 agent 的屏幕报模型/API 暂时性错误，或巡检员 terra 连续 2 次调用失败；屏幕识别新增 "api error"、"held this request"、"without routing"、"gateway"，以及带报错字样的 500/502/504，并认得 Claude Code 的 `❯` 输入框）和 `stall:project`（有节点在跑或就绪，但所有开着的线已 60 分钟没有任何 router/worker 事件）。条件消失时发"[已恢复]"。巡检员（terra）不再拖慢整轮：确定性的工作（代派、自动继续、关终端、催 router、QQ 告警）都在它之前做完；它调用失败（超时或出错）后 60 分钟内不再调，超时上限 600 秒。

**磁盘告警只发给能处理的人。** worker 在哪台机器写盘（live 里 worker 终端所在主机、节点 route 的 `on`，实际是 WSL），agent 就只收到那台机器的"暂停新的大量写盘任务；清理由巡检负责"。Mac 这类不跑 worker 的机器空间低时不再催 agent，而是 QQ 告警 `disk:<主机>:<挂载点>` 给用户自己清理。worker 主机还记下最近 24 小时的可用空间（`patrol.state.json` 的 `disk_hist`），照当前速度不到 12 小时就降到 15 G 时报 `disk_fill_soon` 并发 QQ 告警 `disk_fill:<主机>:<挂载点>`。

**严格条件自动清理工作区（只在 --apply，用户 11-06 批准）。** worker 工作区每个约 2.4 G、从不删除。巡检只删同时满足以下条件的：(1) 派进去过的节点全是 reviewed / superseded / cancelled / failed；(2) 12 小时内没有任何事件提到该路径或这些节点，目录里最新文件也在 12 小时前；(3) 没有任何在线终端或线路配置在用它；(4) 在 WSL 上一次 ssh 脚本验证：`git status --porcelain --untracked-files=all` 为空、它是附属工作区而不是主仓库、HEAD 在别的引用上或它自己的分支还在（删除前后各验一次，orca 默认保留本地分支）；`git -C` 读不了的记为 `worktree_broken`（只报数量，不删）；(5) 每轮最多 20 个，最久没动的先删。命令 `orca worktree rm --environment wsl --worktree path:<路径> --json`，不带 --force 也不带 --delete-branch。每个清理写一条 `observe`（key `wt_rm:<路径>`），并在对应 router 的通知里加一行"已清理 N 个已完成工作区，分支保留"。干跑只列候选和原因，什么都不删。

**就绪节点不许悄悄躺着。** 巡检代派不了的就绪节点（spec 读不到、route 不全、decide 缺选项、代派被 Orca 拒绝）每轮列给 router，不管这条线有没有别的节点在跑：一条消息写明"N 个就绪节点巡检派不出去：节点（原因）…"，同一节点同一原因只催一次，1 小时后再提醒一次。任何就绪节点（自动或手动）超过 45 分钟没派，也进同一条消息（原因"就绪 N 分钟未派"，已被上面列过的不重复；因并行上限、串行段、塌缩暂缓的不算）。巡检自己被 Orca 明确拒绝的代派（报错含 requires / invalid / unknown option / usage / not found / no such，且没有任何 dispatch/task/terminal id）记为 block（env，"代派被 Orca 拒绝，巡检会在修正后重试"），不再永久封死：命令行或 spec 引用变了、或距上次满 60 分钟就重试，先查 Orca 里没有同名工作区的任务，累计最多 3 次，超过发 QQ 告警；超时、回执解析不了、带了部分 id 的失败仍按"不重试"处理。状态记在 `~/.progress/<项目>/patrol.state.json`。

## 8. 落地顺序（在 autotaskgen 里）

1. 图模型扩展：节点结果可为"子图提议"；控制器闸门（无环、深度、写域、预算、验收标准）。
2. 调度器：全局就绪队列、并行上限、serial/parallel 标注与闸门、按"可并行信号"唤醒 router、塌缩检测；worker 交付后自动关闭。
3. 审查与指标：`check` 节点只在关键处生成；看板与巡检加 §7 的指标。
4. 决策分档：`decide` 节点、双模型面板、每日汇总。
5. 沟通：Hermes→QQ 推送决策卡片，先只推送，回复生效后续再接。
6. 领域能力探测：每个领域的已知答案题和失效清单。
